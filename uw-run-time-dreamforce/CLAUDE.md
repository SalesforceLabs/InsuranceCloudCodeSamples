# UW Workbench — Context for Claude

This repo holds **two distinct experiences** that must not be confused with each other:

1. **Runtime** — `src/` — a Next.js + TypeScript demo of the underwriter's workbench. Walks through a 9-step interactive flow: new commercial insurance submission → email arrival → extraction → reconciliation → submission lines with discrepancies.
2. **Setup** — `public/setup/` — a separate vanilla-HTML/CSS/JS app that simulates the Salesforce Setup admin UI used to **configure** the runtime experience (object fields, activities/stages, integrations, assignment rules, etc.). Served as static assets by the same Next.js dev server but otherwise has zero shared code with the runtime.

**Disambiguation rule (IMPORTANT):** When a user request could plausibly apply to either Runtime or Setup (e.g. "add a field", "change the table", "fix the modal", "update the nav"), **ask which one they mean before making changes**. Never silently pick. Phrases like "the workbench / list page / submission record / Run my day / submission lines" are Runtime; "Setup / admin / configuration / object management / assignment rules / integration hub" are Setup. Anything else, ask.

## Runtime ↔ Setup link
- Settings/gear icon in `GlobalHeader.tsx` opens the Setup app via `window.open('/setup/index.html', '_blank')` — Setup launches in a new tab and runs entirely client-side off `public/setup/`.
- The two apps share **nothing** at the code level: no React components, no shared CSS, no shared mock data. Setup mocks its own data in localStorage under `uw_*` keys; Runtime mocks live in `src/data/` (in-memory) and a few `submissionLine_*` localStorage keys.
- If a request says "wire setup to actually configure the workbench", treat that as cross-cutting — confirm scope with the user before threading state between the two.

## Demo flow model
- `useDemoFlow()` exposes `currentStep`, `totalSteps`, `goToStep(n)`, `goToNextStep`, `goToPreviousStep`. Step is persisted to `localStorage.demoFlowStep` and synced across tabs.
- `stepConfigurations[N]` in `demoStepData.ts` carries everything that varies per step: `submission` header field visibility, activities, pendingTasks, documents, emails, slackMessages, progressPath, and Step 9 extras (`submissionLineLOBs`, `submissionLinesWarning`, `submissionLineDiscrepancies`, `submissionLineAttributeSources`, `submissionLinePotentialDuplicates`, `overviewLobTiles`).
- Pages render conditionally on `currentStep` — adding new behavior usually means adding a new field to the step config and reading it in the page.
- Step changer lives at bottom-right (`DemoFlowController.tsx`). It reaches `currentStep` via context. Server renders default `1`; client may resume from localStorage — be careful with hydration.

## What each step roughly represents (1..9)
1. Submission email received — minimal fields, agent kicks off Partial Extraction
2. Email analyzed, fields extracted
3. Manual classification step
4. Qualifying checks (auto + manual)
5. Clearance / appetite checks complete
6. Complete data extraction logged; data reconciliation in progress
7. Reconciliation continues; document summaries persist
8. Reconciliation in progress; submission lines being assembled
9. Reconciliation complete — Commercial Property + General Liability submission lines created with discrepancies; review tasks assigned to Martha

- **View Sources modal** (`lineSourceViewer` state) on the LOB submission-line page (`submission-lines/[id].tsx`): two-pane layout. Left pane = vertical per-source tabs (ACORD 140/125/126/Email, color-coded) + document viewer on a dark canvas with a bookmark-shaped scroll-marker "flag rail". Right pane = attribute rows. Header has a segmented **View Sources / Attribute Mapping** toggle (`viewSourcesMode`, active = `#0176D3`); Attribute Mapping is a "coming soon" placeholder only. Title is just the submission-line name. Right pane has **Mapped / Unmapped** tabs (`viewSourcesTab`) below the "Only show values from the selected doc" checkbox (`viewSourcesOnlyActiveDoc`).
  - **Pool model.** Every extraction is flattened into atomic **pool items** keyed `${lineId}::${attrKey}::${candidateIdx}` (e.g. Chicago "Address" extracted from 3 docs = 3 pool items). Each item is *either* mapped to a canonical term *or* sits in the unmapped pool — it is **never deleted**. `viewSourcesRowMap` (`Record<string,string>`: `''` = returned to pool, term string = mapped, absent = inherit the attribute's default `canonicalTermMappings`) layers on top of the attribute-level mapping so the tree/reconcile behavior elsewhere is untouched. `itemTerm(it)` resolves a row's term; `mappedItems`/`unmappedItems` partition the pool; `mappedGroups` buckets mapped items by canonical term (every catalog term gets a box even when empty).

Empty term box = "No attribute mapped", no border. Per-row **Map** button still maps one row. Clicking a row (not the checkbox/override/map controls) highlights its extracted value in the doc.
  - **Override Value.** Every row (both tabs) has an inline-editable **Override Value** cell (`viewSourcesOverride` keyed by rowKey; `viewSourcesEditingRow` tracks the row being edited). If non-empty it becomes the row's effective value (`displayValue = override || extracted`) while the attribute name + source stay intact; the extracted Value cell renders struck-through/greyed and an amber `OVERRIDE` tag shows in the mapped collapsed header. A ✕ clears it. Doc highlighting still targets the **extracted** value (an override is manual text absent from the source doc).
  - **Flag rail** is tab-aware: `railItems`/`valueToAttr` are scoped to the active tab (`mappedItems` vs `unmappedItems`) so the rail's markers reflect Mapped vs Unmapped. `renderText()` marks matching values; rail marker positions measured in a `useLayoutEffect` keyed on `viewSourcesTab`/`viewSourcesMode`/etc. All View Sources state resets in `closeModal`.
  - Chicago Warehouse (`a01SB00001p8B6rYAE`) is the worked example: candidates for Address/City/State/Zip (×3 docs), Country/Security (×2), Sprinklered/Fire Alarm (×3).

## Coding rules and gotchas
- **Hydration**: components that read `localStorage` (e.g., `useDemoFlow`) must gate any conditional render behind a `mounted` flag, or server output will mismatch client output. The notification panel + badge already do this — copy the pattern.
- **No new files unless asked.** Edit existing ones.
- **No comments unless the *why* is non-obvious.** Don't narrate code.
- **Inline-edit pattern**: clicking a value swaps to `<input autoFocus>`; commit on blur or Enter.
- **List view DOM injection**: `index.tsx` post-renders the SLDS DataTable via a `useEffect` that walks `tbody tr` and rewrites cell innerHTML to add the account link and the NEW badge. If you change column order, the cell indices shift.
- **Demo step is global**: never reach into another component to mutate `demoFlowStep` directly — go through `goToStep`.

## Setup app (`public/setup/`)

**Purpose.** A Salesforce Setup-style admin UI that simulates how an admin would configure the underwriting workbench: object fields, reusable activities, stage configurations, integration connections, email-to-submission, document extraction, and submission assignment rules. Pure demo — no backend.

**Architecture.** Single-page, hash-routed vanilla JS app loaded from one `index.html`. Top header (Salesforce dark `#032D60`) + collapsible left nav tree + content panel + optional right-side agent chat. All screens are sibling `<div class="panel hidden">` blocks (~11 of them). The router hides all panels and unhides the target. There is no build step.

**Routes (hash-based, parsed in `app.js` line ~777 `router()`).** `#/activity-management`, `#/activity-config/:id`, `#/stage-config/:id`, `#/integration-hub`, `#/connection/:id`, `#/document-extraction`, `#/email-to-submission`, `#/email-routing-form`, `#/submission-assignment`, `#/assignment-rule-detail/:id`, `#/rule-entry-form/:id`, `#/object-management`.

**Script load order (must stay in this order — later files patch earlier ones).**
1. `app.js` — router, all panel logic, `localStorage` state, shared utilities (`esc()`, `fmtDate()`).
2. `activities-refactor.js` — Reusable Activities Library: `reusableActivities` array, `renderActivitiesLibraryTable()`, `openActivityLibraryModal()`. Storage key `uw_reusable_activities`.
3. `activity-render-patch.js` — saves the original `buildProcessCell` and replaces it so stage activities can reference library activities by `activityRefId` (with optional `nameOverride`) instead of inlining `action`/`actionDetails`.
4. `activity-management-tabs.js` — adds tabs (`switchActivityManagementTab('activities' | 'stage-management')`) inside the Activity Management panel; overrides the original `openActivityModal` to support activity-reference mode.
5. `agent-chat.js` — right-side simulated Agentforce panel with a scripted `conversation` array and `openAgentChat()` / `sendAgentMessage()` / `nextConversationStep()`.

**State / persistence.** Configuration is stored permanently in `data/setup/config.json` and accessed via Next.js API routes at `/api/setup/config`. The Setup app loads configuration asynchronously via `persistence.js` → `loadConfig()` on page load. Changes are persisted via `saveConfig()` which POSTs to the API. Configuration includes: `fields`, `nextFieldId`, `reusableActivities`, `nextReusableActivityId`, `activityConfigs`, `nextActivityConfigId`, `stageConfigs`, `nextStageConfigId`, `assignmentRules`, `nextAssignmentRuleId`, `connections`, `nextConnectionId`. `DEFAULT_FIELDS` in `app.js` seeds 26 stock Submission fields. Provider catalog (~13 vendors) is hard-coded in `app.js` (`PROVIDERS` array). **Migration:** on first load, `persistence.js` automatically migrates any existing `uw_*` localStorage data to the JSON file.

**UI conventions (Setup).**
- **CSS class prefixes:** `.nav-`, `.integration-hub-`, `.agent-chat-`, plus SLDS-flavored `.slds-table`, `.btn-new` (blue), `.btn-cancel`, `.btn-secondary`, `.btn-agent-chat`. Modals: `.modal-overlay` + `.modal` (variants: `.modal-lg`).
- **Panel IDs** (used by router): `#panel-activity-management`, `#panel-integration-hub`, `#panel-submission-assignment`, `#panel-object-management`, etc.
- **Inline `onclick="…"`** is the dominant event pattern — no event delegation. Keep this style when extending.
- **Tables:** row checkboxes, `.badge-type`, `.badge-active` / `.badge-inactive`, action menus via `rowMenuBtn()`.
- **No third-party libs.** Pure vanilla JS. Only external asset is the Agentforce icon at `http://salesforcetime.com/wp-content/uploads/2025/12/AgentforceIcon.png`.

**Setup-specific gotchas.**
- **Don't reorder the `<script>` tags** in `index.html` — `persistence.js` must load first (defines `loadConfig`, `saveConfig`, getters/setters), then `app.js` and `activities-refactor.js`, then patches (`activity-render-patch.js`, `activity-management-tabs.js`).
- **Async initialization:** `app.js` ends with `async function initializeApp()` that loads config from API before rendering any tables or running the router. All `persist*()` functions are now async and call `saveConfig()`.
- **Two activity reference models** coexist: inline (`action` + `actionDetails`) and library reference (`activityRefId`). When touching activity rendering, check all three of `app.js` `buildProcessCell`, the patch in `activity-render-patch.js`, and the modal logic in `activity-management-tabs.js`.
- **Bust the cache** by bumping the `?v=NN` query string on `<link>` and `<script>` tags in `index.html` after a CSS/JS edit, otherwise the new tab will serve the previous version.
- **Setup state persists to JSON file.** Configuration is stored in `data/setup/config.json` and survives app restarts. Runtime state (`demoFlowStep`, `submissionLine_*`) remains in localStorage and is separate.
- **No SSR concerns** in Setup — it's static HTML, so the `mounted` hydration pattern from Runtime does not apply.
